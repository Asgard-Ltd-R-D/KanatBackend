Problem

  • There are two posting paths. Live posts are queued with retries and a per-run uuid4 key. Recordings post synchronously with no retry and a uuid5 key. Each path has its own urllib code.
  • The worker reads the shared hole dict on its own thread. It is correct only because process calls flush() (1569) before Persistence.end (1596) refreshes the dict in place. That ordering is written down nowhere, and a flush timeout breaks it.
  • process slices _Announcer.announced[prev:] to find what is new (1560–1565).

Solution

When a Bullet Hole is Confirmed, the detection thread snapshots it into an immutable BulletHoleConfirmed, already in the backend's units, and calls publish(event). One WebApp adapter, in its own module, owns the v1 wire format, the key, the queue, retries and the final drain.

Wins

  • Deletes _post_bullets and the announced[prev:] slice
  • Recordings get retries with no new code
  • One idempotency rule instead of two
  • process drops session_id and backend_url
  • Tests pass posted.append, with no urlopen patch
  • Retry, 4xx handling and drain become testable at the adapter's interface (none are tested today)
  • Locality: every HTTP failure is debugged in one module
  • The adapter never touches a hole dict

Correction to the proposal: build the payload on both sides of the seam

  • Detection side, at emit: Board px → template px needs Board space (view.tpl_to_board). The frame → wall clock needs the source (wall_clock). These are domain facts.
  • Adapter side: the field names, the …Z timestamp format, the 0–1405 / 0–1120 clip, version, source: "model" and the key. These are the WebApp's contract.
  • Moving all of it into the adapter means the adapter needs view and wall_clock again. That is today's coupling with a new name.
ADR-0004 says a Confirmed Bullet Hole is never retracted. That is why one event type is enough: there is no update or retract event to design.

Problem

When the adapter builds the payload from a raw hole, it needs Board space and the source's clock. The coupling you wanted to remove comes back. A Protocol with one production adapter is ceremony, and close() on the interface moves the adapter's lifetime into process.

Solution

Take candidate 1 instead. The interface is a plain callable, which Python's duck typing covers. main owns the adapter's lifetime with with.

Top recommendation

Candidate 1: one posting path behind a publish seam

It passes the deletion test. Delete publish, and session_id, backend_url, two urllib copies and two key rules come back into process. Two adapters make it a real seam: the WebApp adapter in production and list.append in tests.

    ...

# detection/webapp.py, the adapter (today's _BulletPostWorker, moved and narrowed)
class WebAppPublisher:
    def __init__(self, session_id, backend_url): ...   # starts the worker thread
    def publish(self, event): self._q.put(event)       # never blocks detection
    def __enter__(self): return self
    def __exit__(self, *exc): self._drain(timeout=120)
    # private: _payload(event, key) v1 JSON · _key(event) uuid5 · _post_with_retry

# main
with WebAppPublisher(a.session_id, a.backend_url) if a.session_id else nullcontext() as pub:
    process(..., publish=pub.publish if pub else None)
